Migraciones

El historial de cómo ha cambiado tu base de datos, escrito en ficheros que se guardan con el código.

⏱ 17 min de lectura

Cambiar un modelo es fácil: se edita una línea. Cambiar una tabla que ya tiene datos dentro, y que además existe en tu máquina, en la de dos compañeros y en el servidor, no lo es. Hay que aplicar el mismo cambio en los cuatro sitios, en el mismo orden, sin perder nada y sabiendo en todo momento cuáles van por dónde.

Las migraciones son la respuesta de Django a eso: cada cambio del modelo se convierte en un fichero de Python que describe la modificación, esos ficheros se guardan en el repositorio junto al código, y cada base de datos lleva la cuenta de cuáles ha aplicado. Es control de versiones para la forma de tus tablas.

Qué vas a aprender

Entender la diferencia entre makemigrations y migrate y por qué están separadas, leer un fichero de migración, saber cómo lleva Django la cuenta de lo aplicado, deshacer una migración, escribir una migración de datos con RunPython, y resolver los dos problemas habituales: el campo obligatorio añadido a una tabla con filas y el conflicto de dos migraciones con el mismo número.

Dos órdenes y por qué son dos#

bash
python manage.py makemigrations

Compara tus modelos con el estado que describen las migraciones que ya hay, y escribe un fichero con las diferencias. No toca la base de datos. Ni siquiera necesita que haya una.

bash
python manage.py migrate

Mira qué migraciones hay escritas, qué migraciones se han aplicado ya en esta base de datos, y ejecuta las que falten.

La separación es lo que hace que el sistema sirva para algo. El fichero que genera la primera es un artefacto que se guarda en el repositorio, se revisa como cualquier otro código y viaja con él. Cuando alguien se baja tu rama, no ejecuta makemigrations: ejecuta migrate y su base de datos acaba exactamente igual que la tuya, con los mismos pasos y en el mismo orden.

Las migraciones se suben al repositorio

Es la confusión más común al empezar, seguramente porque la carpeta se parece a otras que sí se ignoran. La carpeta migrations/ y todo lo que hay dentro van al control de versiones. No son ficheros generados que se puedan rehacer: son el historial, y sin ellos nadie puede reconstruir la base de datos paso a paso.

Lo que no va al repositorio es db.sqlite3, que sí es tuyo y se regenera.

La señal de que alguien ha hecho esto mal es que dos personas del equipo tienen migraciones distintas con el mismo número, o que aparecen migraciones nuevas que crean tablas que ya existen.

Cómo es un fichero de migración#

El de la agenda, generado al escribir el modelo:

contactos/migrations/0001_initial.py
# Generated by Django 6.1.1 on 2026-09-22 16:16

from django.db import migrations, models


class Migration(migrations.Migration):

        initial = True

    dependencies = [
    ]

    operations = [
        migrations.CreateModel(
            name='Contacto',
            fields=[
                ('id', models.BigAutoField(auto_created=True, primary_key=True,
                                           serialize=False, verbose_name='ID')),
                ('nombre', models.CharField(max_length=100, verbose_name='nombre')),
                ('correo', models.EmailField(max_length=254, unique=True, verbose_name='correo')),
                ('telefono', models.CharField(blank=True, max_length=20, verbose_name='teléfono')),
                ('grupo', models.CharField(default='sin', max_length=15, verbose_name='grupo')),
                ('notas', models.TextField(blank=True, verbose_name='notas')),
                ('creado', models.DateTimeField(auto_now_add=True, verbose_name='creado')),
            ],
        ),
    ]

Es código Python normal, y se puede leer y editar. Tres partes:

dependencies dice qué migraciones tienen que estar aplicadas antes que esta. Aquí está vacía porque es la primera. Eso es lo que forma el grafo: las migraciones no son una lista ordenada por su número, son un grafo de dependencias, y el número del nombre es solo una comodidad para leerlas.

operations es lo que hay que hacer. Hay unas quince operaciones posibles —CreateModel, AddField, AlterField, RemoveField, RenameField, RunPython, RunSQL— y cada makemigrations produce las que correspondan.

initial = True marca la primera de la aplicación.

Fíjate en que el choices del campo grupo no aparece. Eso no es un olvido: choices no afecta a la base de datos, como se vio en la lección anterior, y Django lo omite para no generar migraciones inútiles cada vez que cambies una etiqueta.

Cómo sabe Django lo que falta#

En una tabla. Está en tu base de datos desde el primer migrate:

consola
>>> import sqlite3
>>> c = sqlite3.connect('db.sqlite3')
>>> list(c.execute("SELECT app, name, applied FROM django_migrations WHERE app='contactos'"))
[('contactos', '0001_initial', '2026-09-22 16:22:43.017800')]

Una fila por migración aplicada, con la fecha. Eso es todo el mecanismo: migrate compara los ficheros que hay en disco con las filas de esa tabla y ejecuta la diferencia.

La forma cómoda de verlo:

bash
python manage.py showmigrations contactos
Salida en pantalla
contactos
 [X] 0001_initial
 [X] 0002_contacto_empresa
 [ ] 0003_normalizar_grupos

La cruz significa aplicada. Es lo primero que hay que mirar cuando una base de datos no tiene la forma que debería.

Añadir un campo#

Añade empresa al modelo y ejecuta makemigrations:

Salida en pantalla
It is impossible to add a non-nullable field 'empresa' to contacto without specifying
a default. This is because the database needs something to populate existing rows.
Please select a fix:
 1) Provide a one-off default now
 2) Quit and manually define a default value in models.py.
Select an option:

Esta pregunta desconcierta la primera vez y es completamente razonable. La tabla ya tiene dos filas. El campo nuevo es obligatorio. ¿Qué se pone en las filas que ya existen? Nadie más que tú puede contestarlo.

Hay tres salidas:

  • Un valor de una vez, la opción 1. Django lo pone en las filas existentes y no lo deja en el modelo.
  • Un default en el modelo, la opción 2. Es lo mismo pero permanente, y conviene si el valor tiene sentido también para las filas futuras.
  • blank=True, que es lo que suele querer decirse en un campo de texto. Entonces la cadena vacía es un valor válido y Django deja de preguntar.

Con blank=True, el fichero que sale:

contactos/migrations/0002_contacto_empresa.py
class Migration(migrations.Migration):

        dependencies = [
        ('contactos', '0001_initial'),
    ]

    operations = [
        migrations.AddField(
            model_name='contacto',
            name='empresa',
            field=models.CharField(blank=True, max_length=100, verbose_name='empresa'),
        ),
    ]

En SQLite, añadir una columna es rehacer la tabla entera

Mira el SQL de esa migración tan sencilla:

Salida en pantalla
CREATE TABLE "new__contactos_contacto" (...);
INSERT INTO "new__contactos_contacto" ("id", "nombre", ..., "empresa")
    SELECT "id", "nombre", ..., '' FROM "contactos_contacto";
DROP TABLE "contactos_contacto";
ALTER TABLE "new__contactos_contacto" RENAME TO "contactos_contacto";

No hay ningún ALTER TABLE ADD COLUMN. Django crea una tabla nueva, copia los datos, borra la vieja y renombra, porque SQLite no sabe hacer la mayoría de las modificaciones de columnas y esa es la forma estándar de esquivarlo.

Tiene dos consecuencias prácticas. Con una tabla grande, esa migración tarda y ocupa el doble de espacio mientras dura. Y explica por qué el mismo cambio se comporta distinto en SQLite y en PostgreSQL, que sí tiene ALTER TABLE: son diferencias del gestor, no de Django, y se notan el día que se cambia de uno a otro, que es la lección 41.

Deshacer#

Se migra hacia atrás indicando hasta dónde:

bash
python manage.py migrate contactos 0001
Salida en pantalla
Unapplying contactos.0002_contacto_empresa... OK

Django ejecuta las operaciones a la inversa: donde había un AddField, quita la columna. showmigrations pasa a enseñar la casilla vacía, y para volver adelante basta con migrate contactos.

Esto funciona bien y conviene saber lo que no recupera: los datos de una columna eliminada no vuelven. Deshacer un AddField borra la columna con lo que tuviera dentro; volver a aplicarla la crea vacía. La reversibilidad es de la estructura, no del contenido.

Y hay operaciones que no se pueden deshacer en absoluto, señaladas con IrreversibleError al intentarlo. Un RunSQL sin SQL inverso es una de ellas.

Para empezar de cero en desarrollo

Mientras estás experimentando con los modelos, lo más rápido no es deshacer migraciones una por una:

bash
rm db.sqlite3
rm contactos/migrations/0*.py
python manage.py makemigrations
python manage.py migrate

Eso vale solo mientras la base de datos no tenga nada que te importe y el proyecto no esté compartido con nadie. En cuanto haya datos de verdad o alguien más tenga tus migraciones, ese atajo es exactamente lo que no se puede hacer, y el camino es una migración más.

Migraciones de datos#

Todo lo anterior cambia la forma de las tablas. A veces hay que cambiar el contenido: pasar todos los grupos a minúsculas, partir un campo de nombre completo en dos, rellenar una columna nueva a partir de otra.

Eso también es una migración, y se crea vacía:

bash
python manage.py makemigrations contactos --empty --name normalizar_grupos

Y se rellena con RunPython:

contactos/migrations/0003_normalizar_grupos.py
from django.db import migrations


def poner_en_minusculas(apps, schema_editor):
        Contacto = apps.get_model('contactos', 'Contacto')
    for contacto in Contacto.objects.all():
                contacto.grupo = contacto.grupo.lower()
        contacto.save(update_fields=['grupo'])


def volver_atras(apps, schema_editor):
        Contacto = apps.get_model('contactos', 'Contacto')
    for contacto in Contacto.objects.all():
                contacto.grupo = contacto.grupo.capitalize()
        contacto.save(update_fields=['grupo'])


class Migration(migrations.Migration):

        dependencies = [
        ('contactos', '0002_contacto_empresa'),
    ]

    operations = [
        migrations.RunPython(poner_en_minusculas, volver_atras),
    ]

Funciona en los dos sentidos:

Salida en pantalla
antes:        [('Ana Ruiz', 'TRABAJO'), ('Luis Pardo', 'familia')]
despues:      [('Ana Ruiz', 'trabajo'), ('Luis Pardo', 'familia')]
tras deshacer:[('Ana Ruiz', 'Trabajo'), ('Luis Pardo', 'Familia')]

La segunda función es opcional y conviene escribirla siempre que se pueda: es lo que hace la migración reversible. Cuando de verdad no hay vuelta atrás, se pone migrations.RunPython.noop, que deja claro que se ha pensado.

apps.get_model y no from contactos.models import Contacto

Esta es la regla que hay que respetar en toda migración de datos, y saltársela produce un fallo que no aparece hoy sino dentro de seis meses.

La primera línea de la función:

python
Contacto = apps.get_model('contactos', 'Contacto')

Ese apps no es el de tu código: es una reconstrucción histórica del modelo tal como era en este punto del historial. Si importas el modelo de verdad, estás usando el de hoy.

La diferencia no se nota al escribir la migración, porque hoy los dos son iguales. Se nota cuando alguien monta el proyecto desde cero dentro de un año: las migraciones se aplican en orden desde la primera, y al llegar a esta el modelo de verdad ya tiene tres campos más, uno obligatorio que aún no existía. La migración revienta, y el mensaje habla de una columna que no tiene nada que ver con lo que estás mirando.

El modelo histórico tiene un límite que conviene conocer: no trae los métodos que escribiste tú, solo los campos y el gestor. Si la migración necesita lógica, se copia dentro del fichero de la migración.

Los dos problemas de trabajar en equipo#

Dos migraciones con el mismo número. Tu compañera y tú añadís un campo cada uno en vuestra rama, las dos migraciones se llaman 0004_algo y dependen de la 0003. Al juntarlas:

Salida en pantalla
CommandError: Conflicting migrations detected; multiple leaf nodes in the migration
graph: (0004_a, 0004_b in contactos).
To fix them run 'python manage.py makemigrations --merge'

El mensaje trae la solución. --merge crea una migración vacía que depende de las dos y vuelve a dejar un solo final en el grafo. No hay que renumerar nada ni elegir cuál sobra: las dos se quedan.

Alguien ha cambiado un modelo y no ha generado la migración. Eso se detecta antes de que llegue a nadie, con una orden pensada para la integración continua:

bash
python manage.py makemigrations --check --dry-run

No escribe nada y termina con código de error si faltan migraciones por generar. Es una línea en el guion de pruebas, y evita la situación de bajarse una rama y encontrarse la base de datos sin la columna que el código ya usa.

Cuando hay demasiadas: squashmigrations

A los dos años, una aplicación viva tiene sesenta migraciones y aplicarlas todas desde cero tarda. squashmigrations las resume en una sola equivalente:

bash
python manage.py squashmigrations contactos 0003

Al terminar avisa de dos cosas importantes. Que las antiguas se dejan en su sitio hasta estar seguro de que todas las instalaciones han pasado de ese punto. Y que si había migraciones de datos, el código de sus funciones hay que copiarlo a mano:

Salida en pantalla
Manual porting required
  Your migrations contained functions that must be manually copied over,
  as we could not safely copy their implementation.

No es una operación para hacer con prisa, y no hace falta en un proyecto joven. Basta con saber que existe.

En resumen

Una migración es un fichero de Python que describe un cambio en la estructura de la base de datos, y el conjunto de esos ficheros es el historial de cómo ha llegado a ser lo que es. makemigrations compara los modelos con las migraciones que ya hay y escribe la diferencia sin tocar nada; migrate aplica a esta base de datos lo que le falte, y lleva la cuenta en una tabla llamada django_migrations. Están separadas porque el fichero se guarda en el repositorio y viaja con el código: la carpeta migrations/ va al control de versiones, y db.sqlite3 no. Dentro de cada fichero hay unas dependencias, que forman un grafo y no una lista, y unas operaciones. Añadir un campo obligatorio a una tabla con filas hace que Django pregunte qué poner en las que ya existen, y en un campo de texto la respuesta suele ser blank=True. En SQLite, cualquier cambio de columna se hace creando una tabla nueva, copiando y renombrando, porque el gestor no sabe hacer otra cosa. Se puede migrar hacia atrás indicando hasta qué número, recordando que se recupera la estructura pero no los datos de una columna borrada. Los cambios de contenido también son migraciones, se crean vacías con --empty y se rellenan con RunPython, y dentro hay que pedir el modelo con apps.get_model para usar la versión histórica y no la de hoy. En equipo, dos migraciones con el mismo número se arreglan con makemigrations --merge, y makemigrations --check en el guion de pruebas avisa de los modelos cambiados sin migración.

Practica

  1. Añade un campo empresa obligatorio con la tabla ya poblada y lee la pregunta de makemigrations. Prueba las tres salidas: valor de una vez, default en el modelo y blank=True.
  2. Mira el SQL de esa migración con sqlmigrate y localiza la tabla new__ que crea SQLite. Cuenta cuántas instrucciones hacen falta para añadir una columna.
  3. Deshaz la migración, comprueba con showmigrations que la casilla se ha vaciado y consulta la tabla django_migrations con sqlite3 para ver que la fila ha desaparecido.
  4. Escribe una migración de datos que ponga en mayúscula la primera letra de todos los nombres, con su función de vuelta atrás. Aplícala, deshazla y comprueba las dos direcciones.
